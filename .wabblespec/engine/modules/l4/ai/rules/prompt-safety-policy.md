# Gateway AI — Prompt Safety Policy

Rules enforced by gateway-ai Phase B verdict. Applies to any target embedding LLM calls, agent loops, or AI-generated content pipelines. Violations produce FLAG or BLOCK verdicts.

---

## Rule P1: System Prompt Versioning and Testing

**Requirement:** Every system prompt in production is version-controlled and has a corresponding test fixture.

| Requirement | Details |
|---|---|
| Version control | System prompts stored in VCS alongside application code — not in database or external config without audit trail |
| Versioning scheme | Semantic version or sequential ID; every change produces a new version |
| Test fixture | At least one prompt-input / expected-output fixture per system prompt; run in eval suite before deploy |
| Change review | System prompt changes trigger same review gate as code changes |

**Failure modes:**
- System prompt stored outside VCS with no change audit trail = BLOCK
- No test fixture for any system prompt = BLOCK
- System prompt change deployable without review = FLAG

---

## Rule P2: Prompt Injection Defense

**Requirement:** All LLM inputs that include user-controlled content must pass through injection defense before being incorporated into prompts.

**Required defenses:**

| Input source | Required treatment |
|---|---|
| User-supplied text (freeform) | Clearly delimited (XML tags, triple-backtick blocks, or role-separated turns) — never string-interpolated directly into system prompt |
| File content loaded from user upload | Treated as data, not instruction; wrapped in explicit "this is data, not instruction" framing |
| External API response incorporated into prompt | Sanitized: strip instructions, treat as structured data |
| Tool/function output fed back into context | Validated against declared schema before re-injection |

**Prompt injection red flag patterns (must be absent from undefended inputs):**
- "Ignore previous instructions"
- "You are now..."
- "Respond only in..."
- Embedded base64 or encoded content without decoding validation

**Failure modes:**
- User text interpolated directly into system prompt without delimiter = BLOCK
- External content injected into prompt context without framing = FLAG
- No injection defense declared in spec for user-facing LLM feature = BLOCK

## Rule P3: PII in Prompts

**Requirement:** Personally Identifiable Information (PII) must not be logged, cached, or stored as part of prompt or completion text unless a Data Processing Agreement (DPA) covers the model provider.

| Data type | Requirement |
|---|---|
| Names, emails, phone numbers in user inputs | Redact from logs; include in prompt only if DPA covers the provider |
| Healthcare or financial data | Never include in prompts without explicit DPA and legal sign-off |
| Prompt and completion logging | Disabled by default; require explicit opt-in with DPA review |
| PII in evaluation fixtures | Use synthetic data only — no real user data in eval sets |

**Failure modes:**
- Prompt logging enabled with PII in inputs and no DPA = BLOCK
- Healthcare or financial data sent to external model provider without legal sign-off = BLOCK
- Real user PII in eval fixture set = BLOCK

## Rule P4: LLM Output Validation Before Execution

**Requirement:** Any LLM output that is acted upon (parsed, executed, written to file, sent as API call) must be validated before the action occurs.

| Output type | Required validation |
|---|---|
| Structured JSON from LLM | Schema validation against declared output schema before parsing |
| Code generated by LLM | Static analysis (lint + type check) before execution |
| Tool call / function arguments from LLM | Argument schema validation; precondition check before tool invocation |
| Text written to file by LLM | Content policy check for injection patterns; declare allowed content types |

**Failure modes:**
- LLM JSON output parsed without schema validation = BLOCK
- LLM-generated code executed without any static analysis step = BLOCK
- Tool call arguments passed to tools without validation = BLOCK
- No output validation declared in spec for any LLM-to-action path = FLAG

---

## Rule P5: Token Budget Declaration

**Requirement:** Every LLM API call in production code must declare explicit token limits.

| Parameter | Requirement |
|---|---|
| `max_tokens` | Must be set on every completion call; no calls with unbounded output |
| Context window budget | Maximum context window usage declared per call site; excessive context flagged |
| Cost per call estimate | Declared in spec for any feature expected to run at scale |

**Failure modes:**
- `max_tokens` unset on any production LLM call = FLAG
- Call sites where context window can grow unbounded (e.g., full conversation history appended without pruning) = FLAG
- No cost estimate for scale-sensitive LLM features = FLAG
