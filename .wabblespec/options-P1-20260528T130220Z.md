## Decision point

The brainstorm surfaced 28 concrete findings (4 critical, 10 high, 9 medium, 4 low) and five candidate strategies. The user's request has two halves: (a) *solve the existing technical debt, misconnections, broken paths and gaps now*, and (b) *have a solid foundation before integrating ~1000 more references*. The decision is which strategy best serves both halves within reasonable cost. The five brainstorm strategies (A Severity Triage, B doctor+Gate, C Two-Wave, D Schema Consolidation, E Stress-Test First) consolidate into four distinct, implementable proposals below. Schema consolidation (brainstorm D) is folded into Option 2's drift-prevention layer rather than standing alone, because schema gaps are a subset of the drift class the gate must police.

## Option 1: Fix-Now Triage

**Summary:** Fix all 28 findings in severity order (C → H → M → L). Build no new tooling.

**How it works:** One task card, ~6-8 waves. Wave 1 fixes C1-C4 (receipt index path, platform skill IDs, archive.py path, CLAUDE.md version/count drift). Waves 2-4 fix H1-H10 (schema/CLI drift, entity-graph regen, orphan templates, missing schemas, scripts duplication). Wave 5 bundles M1-M9 housekeeping. Optional Wave 6 sweeps L1-L4. Each fix gets a standard Verifier receipt.

**Tradeoffs:**
| Dimension | Assessment |
|---|---|
| Complexity | Low — mostly mechanical edits |
| Time to implement | Medium — 6-8 waves |
| Risk | Medium — no regression net; same drift classes can silently return at scale |
| Reversibility | Easy — each fix is small and git-revertible |
| Fits scope | Partially — solves (a) fully, serves (b) weakly |

**When to choose this:** If the priority is reaching a clean state fast and the team accepts re-auditing manually after the reference surge.

**When NOT to choose this:** If silent drift recurrence during 1000-reference intake is unacceptable. Triage leaves no detector, so the next audit is another full four-agent sweep.

## Option 2: Fix + Permanent Drift Gate  *(recommended)*

**Summary:** Fix the critical and high findings, AND build a `wabblespec-doctor.py` that re-checks every finding class, wired as an `on_archive` daemon job and a Guard advisory layer. Close the schema gaps so the largest drift class becomes structurally impossible.

**How it works:**
- Wave 1: build `wabblespec-doctor.py` consolidating all 28 finding checks (path resolution, receipt-index parity, registry/skills ID parity, doc/version agreement, entity-graph freshness, orphan templates, schema validity).
- Wave 2: close schema gaps (recipe.json, wave-queue.json, delivery-receipt, brainstorm/propose receipt builders — H4/H8 plus this very session's missing propose builder) and unify the `confidence` field (H1, H2).
- Wave 3: fix C1-C4 (the breakages the doctor will otherwise flag forever).
- Wave 4: fix remaining high tier (C2 platform IDs, H3 CLI flags, H5 entity-graph regen, H6/M9 doc + skill path drift, H7 orphan templates, H10 dedup).
- Wave 5: wire doctor into `daemon-config.json` (`on_archive`) and add it as a non-blocking Guard layer. M/L-tier findings are left for the doctor to surface on each run rather than fixed exhaustively now.

**Tradeoffs:**
| Dimension | Assessment |
|---|---|
| Complexity | Medium-High — one new script + schema work + gate wiring |
| Time to implement | Medium-Large — ~5 waves |
| Risk | Medium — a new gate can false-positive; mitigated by shipping it advisory (non-blocking) first |
| Reversibility | Moderate — fixes revert easily; the gate is removable but touches daemon-config and Guard |
| Fits scope | Yes — serves (a) for critical/high and (b) by preventing recurrence |

**When to choose this:** If the foundation must stay clean *while* 1000 references land — the doctor catches new drift at every Archive instead of at the next manual audit.

**When NOT to choose this:** If adding a 43rd permanent script and a Guard layer is unwanted overhead, or if the M/L-tier housekeeping must all be resolved immediately rather than tracked.

## Option 3: Phased Normalize-then-Harden

**Summary:** Two strictly separated passes. Wave-set 1 is pure normalization (renames, path corrections, no logic change). Wave-set 2 adds tests, schemas, and gates over the normalized surface.

**How it works:** Wave-set 1 (mechanical): C1, C2, C3, C4, H1, H2, H3, H6, M8, M9, H7 — all rename/path/doc fixes, independently verifiable, low-risk. Wave-set 2 (hardening): schema files (H8), full test harness for all 42 shared scripts (H9), memory-bootstrap dedup (H10), entity-graph regen daemon (H5), Forget/Reverify sweep (M1/M2/M5), session cleanup (M3), runtime re-probe (M4), README/CONTRIBUTING (M6), `_shared/dev` reconcile (M7), central paths module (L1, L2). ~10 waves total.

**Tradeoffs:**
| Dimension | Assessment |
|---|---|
| Complexity | High — two full passes, test authoring across 42 scripts |
| Time to implement | Large — ~10 waves |
| Risk | Medium — large surface, but clean phasing keeps per-wave risk low |
| Reversibility | Moderate — Wave-set 1 trivially reverts; Wave-set 2 infra harder |
| Fits scope | Yes (most complete) — but exceeds the minimum needed to begin scaling |

**When to choose this:** If the goal is maximum durability and a full test net before any reference work, and the longer timeline is acceptable.

**When NOT to choose this:** If time-to-scaling matters. Front-loading tests for all 42 scripts and all housekeeping delays the reference work that motivated the hardening.

## Option 4: Scale-First Empirical

**Summary:** Build a stress harness that simulates the 1000-reference load first. Fix only what cracks under load.

**How it works:** Wave 1 builds `stress-loader.py` generating 1000 synthetic ref-eval drawers, entity-graph edges, and receipts. Wave 2 runs it and measures which scripts time out, OOM, emit malformed output, or break invariants (C1 receipt-path will surface here if it would in production). Waves 3+ fix observed failures in crack-severity order. Final wave keeps the stress-test as a regression gate.

**Tradeoffs:**
| Dimension | Assessment |
|---|---|
| Complexity | Medium — synthetic corpus generator |
| Time to implement | Medium upfront, variable downstream |
| Risk | Medium-High — synthetic load may not match real distribution; cosmetic/doc debt and latent bugs that don't surface under load are missed |
| Reversibility | Easy — harness is additive, fixes targeted |
| Fits scope | Partially — serves (b) strongly, (a) weakly |

**When to choose this:** If the only real concern is scale behavior and known cosmetic/doc debt can be ignored.

**When NOT to choose this:** If "solve the debts and gaps" (half a of the request) is a first-class goal. This option deliberately ignores anything that survives synthetic load.

## Recommendation

**Option 2 — Fix + Permanent Drift Gate.** It is the only option that serves both halves of the request: it fixes the critical and high findings now (half a), and it leaves behind a `wabblespec-doctor` detector plus closed schema gaps so the same drift classes cannot silently reaccumulate as 1000 references land (half b). Option 1 fixes but installs no detector, so drift returns at scale. Option 3 is the most durable but front-loads a full 42-script test harness and all housekeeping — work that can instead be *surfaced* by the doctor and resolved incrementally, so its ~10-wave cost delays the reference work that motivated this. Option 4 is too narrow for the "solve the debts and gaps" half.

Two notes carried to Specify/Plan:
1. **Reviewer gate at Plan stage.** Option 2 (and 3) wire a new layer into Guard, which is invariant-enforcing and "cannot be bypassed." Adding to it is architectural — route the Plan to Reviewer before Executor. Mitigation already baked in: ship the doctor *advisory/non-blocking* first, promote to blocking only after it runs clean across several Archives.
2. **Option 3's test harness (H9) is the main thing Option 2 defers.** Recommend it as a fast-follow task card once the gate is live, rather than a blocker for scaling.

This recommendation is advisory. The selected option becomes the input to Specify.
