## 3. Top strategy options

Five strategies surfaced. They are described — not ranked or compared. Propose evaluates.

### Option A — Severity Triage

**One-liner**: Walk the finding table top-to-bottom. Critical → High → Medium → Low, no other ordering principle.

**Philosophy**: Minimize time-to-stable. Don't build new tooling. Fix what's broken in priority order, write standard Verifier receipts per fix, move on.

**Scope (in)**: All 28 findings listed above, in numbered order.
**Scope (out)**: New audit tools, test harness, schema-system overhauls, freezes.

**Phasing**:
1. C1–C4 (4 critical, 1 wave each or batched as one wave)
2. H1–H10 (10 high, ~3 waves)
3. M1–M9 (9 medium, 1 wave bundle)
4. L1–L4 (4 low, optional sweep wave)

**Effort signal**: Medium. Wave count ≈ 6-8.
**Trade-off profile**: Prioritizes speed and concreteness; deprioritizes root-cause prevention. Same drift class may reappear without structural change.

---

### Option B — `wabblespec-doctor` + Drift Gate

**One-liner**: Build one audit script that re-runs every finding check; wire it into `daemon-config.json` as `on_archive` and as Guard's Layer 6.

**Philosophy**: Convert one-time audit into permanent gate. Any future drift is caught at the next Archive, not at the next foundation-hardening brainstorm.

**Scope (in)**:
- New `wabblespec-doctor.py` consolidating all 28 finding checks (path resolution, schema validity, registry/skills parity, doc/version agreement, entity-graph freshness, orphan templates).
- Daemon job entry + Guard hook integration.
- Then fix C1–C4 and H1–H4 (highest-impact subset).

**Scope (out)**: Fixing M-tier and L-tier (the doctor surfaces them; humans triage later).

**Phasing**:
1. Build `wabblespec-doctor.py` + Guard wire-up (1 wave).
2. Fix C-tier (1 wave).
3. Fix H1–H4 (1 wave).
4. Daemonize + commit; doctor catches the rest on next run.

**Effort signal**: Medium-large upfront, very low ongoing.
**Trade-off profile**: Prioritizes permanence and detection coverage; deprioritizes immediate cleanup of all findings (M/L tiers persist until next round).

---

### Option C — Two-Wave Normalize-then-Harden

**One-liner**: Wave 1 is pure renaming + path correction (no logic change). Wave 2 adds tests, schemas, and drift gates over the now-normalized surface.

**Philosophy**: Separate "make it consistent" from "make it bulletproof." Each wave is independently verifiable. Wave 1 fixes are mechanical and low-risk; Wave 2 builds on stable ground.

**Scope (Wave 1 — Normalization)**:
- Receipt index path fix (C1)
- Platform skill ID rename (C2)
- archive.py path fix (C3)
- CLAUDE.md version + module-count + script-location updates (C4, H6)
- CLI flag unification (`--delta-class` everywhere) (H3)
- Confidence field unification (`confidence` only) (H1)
- Delivery receipt field name fix (H2)
- Brainstorm receipt builder gap (H4)
- Skill output path drift (M9)
- Legacy recipe.json removal + sunset (M8)
- Orphan template adoption-or-removal decision (H7)

**Scope (Wave 2 — Hardening)**:
- Schema files for recipe.json + wave-queue.json (H8)
- Test harness for shared scripts (H9)
- Memory-bootstrap deduplication (H10)
- Entity-graph regeneration daemon (H5)
- Forget+Reverify sweep (M1, M2, M5)
- Cleanup leftover session dirs (M3)
- Refresh runtime-state.json (M4)
- README/CONTRIBUTING (M6)
- `_shared/dev` reconcile (M7)
- Central paths module + dep-install hints (L1, L2)

**Effort signal**: Large. ~10 waves total.
**Trade-off profile**: Prioritizes thoroughness and clean phasing; deprioritizes time-to-first-fix. No new permanent gates unless Wave 2 includes them.

---

### Option D — Schema-Driven Consolidation

**One-liner**: Treat all drift as a missing-schema problem. Close every schema gap, then enforce all writes through schemas. Other findings fall out as side-effects.

**Philosophy**: Most drift (H1, H2, H4, H8) is field-name disagreement between writer and consumer. Centralize the contract — drift becomes structurally impossible because every write is schema-validated.

**Scope (in)**:
- Add missing schemas: `recipe.schema.json`, `wave-queue.schema.json`, `delivery-receipt.schema.json` extensions, `brainstorm-receipt.schema.json` extension fields.
- Enforce `--validate` on every receipt write in `receipt-writer.py`.
- Unify confidence field across all receipts (`confidence: number 0-1`).
- Wire `quality-floor-check.py` to fail when any receipt fails schema validation.
- Fix C1 (path) and C2 (ID mismatch) as part of the consolidation because they are also "contract drift."

**Scope (out)**: Tests, docs, orphan templates, housekeeping (M-tier, L-tier).

**Phasing**:
1. Schema-gap closure (1 wave).
2. Writer/builder unification (1 wave).
3. Validation enforcement (1 wave).
4. C1/C2 contract fixes (1 wave).

**Effort signal**: Medium.
**Trade-off profile**: Prioritizes structural prevention of one specific debt class; deprioritizes everything outside schema-shaped problems (housekeeping, docs, tests).

---

### Option E — Reference-Ripple Stress-Test First

**One-liner**: Before any cleanup, simulate the 1000-reference load. Generate synthetic drawers, receipts, and skill entries at that scale and observe which subsystems crack first. Fix only what fails under load.

**Philosophy**: The user's stated motivation is scale. Treat hardening as a load problem, not a debt-list problem. The audit findings are hypotheses; the stress test is the experiment.

**Scope (in)**:
- Build `stress-loader.py` generating 1000 synthetic ref-eval drawers + entity-graph edges + receipt entries.
- Run it; observe which scripts time out, OOM, produce malformed output, or break invariants.
- Fix only what cracks, in order of crack severity.
- C1 (receipt path) will surface during this test if it would surface in production.

**Scope (out)**: Anything that doesn't break under synthetic load (the orphan templates, doc drift, leftover dirs — they survive scale).

**Phasing**:
1. Build stress-loader + corpus generator (1 wave).
2. Run + measure (1 wave).
3. Fix observed failures (variable, 2-4 waves).
4. Re-run stress-test as regression gate.

**Effort signal**: Medium upfront, variable downstream.
**Trade-off profile**: Prioritizes empirical evidence and the actual user motivation; deprioritizes cosmetic drift, documentation accuracy, and bugs that don't surface under synthetic load. Risks missing latent bugs that only surface at production-distribution scale.

## 4. Open questions for Propose

1. **Is the goal "1000 refs without breakage" or "framework hardened by every available metric"?** Determines whether Option E's narrow scope is acceptable or whether broader coverage is needed.
2. **How much new infrastructure tolerance?** Options B and D add permanent machinery; A and C don't. The framework already has 42 shared scripts — does it want a 43rd permanent gate, or is leaner preferred?
3. **Wave count vs atomicity?** Option C runs ~10 waves with clean phasing; Option A could be batched smaller. The user's preferred unit of work matters.
4. **Is documentation drift (C4, H6) a Critical or a Medium concern?** Listed as Critical because it misleads contributors and `/brainstorm` style audits, but it doesn't break runtime.
5. **Should Option A be combined with a slimmed B (drift detection only, no new fixes) as a hybrid?** Brainstorm did not generate hybrid options to maintain divergence; Propose may.
