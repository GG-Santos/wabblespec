## 1. SKILL.md

**Always required.** Core orchestration file.

```markdown
---
name: {skill-name}
description: {trigger-optimized description, imperative form, under 1024 chars}
---

# {Skill Title}

{One-paragraph mission statement}

## Process

### Step 1: {Name}
{Instructions — explain WHY, not just WHAT}

### Step 2: {Name}
{Instructions}

## Component Map

| Component | When to Load | Purpose |
|-----------|-------------|---------|
| `scripts/{name}.py` | When {condition} | {Purpose} |
| `references/{name}.md` | When {condition} | {Purpose} |
| `agents/{name}.md` | When spawning {task} | {Purpose} |

## Output Format
{Expected output structure}
```

**Key rules:**
- Under 500 lines; use references for overflow
- Explain WHY behind each instruction
- Include a Component Map table if components exist
- All "when to use" info goes in the frontmatter description, not the body

## 2. skill-rules.json

**Required for Standard tier and above.** Activation patterns and progressive loading.

```json
{
  "version": "1.0",
  "skill_name": "{skill-name}",
  "activation_patterns": [
    {
      "pattern": "{regex or keyword}",
      "weight": 0.8,
      "context": "user_message",
      "description": "When user asks about {thing}"
    },
    {
      "pattern": "{negative pattern}",
      "weight": -0.5,
      "context": "user_message",
      "description": "NOT when user asks about {other thing}"
    }
  ],
  "progressive_loading": {
    "level_1": {
      "description": "Always loaded",
      "files": ["SKILL.md"]
    },
    "level_2": {
      "description": "Loaded when skill activates",
      "files": ["references/*.md", "schemas/*.json"]
    },
    "level_3": {
      "description": "Loaded on demand by SKILL.md instructions",
      "files": ["scripts/*.py", "data/*.csv", "templates/*.j2"]
    }
  },
  "required_capabilities": [],
  "incompatible_skills": []
}
```

## Plugin Metadata (plugin/)

Full factory outputs include plugin metadata so the generated artifact is not
only a skill folder. The default scaffold is runtime-neutral; when the user
targets a specific runtime, isolate those details in an optional runtime
section or handoff note.

```json
{
  "name": "{skill-name}",
  "version": "0.1.0",
  "description": "{short description}",
  "author": {"name": "Generated by skill-factory"},
  "license": "UNLICENSED",
  "surface_registry": "surfaces.json"
}
```

**Key rules:**
- Keep metadata short and install-focused.
- Use `commands/`, `hooks/`, `agents/`, and `mcp/` for behavior; do not bury behavior in `plugin.json`.
- Include `surfaces.json` mapping skill, activation, commands, hooks, MCP server, agents, schemas, evals, and templates.
- Include a plugin README explaining install/run readiness.

## 3. agents/

**Subagent role definitions.** Portable role prompts for delegated analysis,
execution, review, grading, and handoff work.

```markdown
---
name: {agent-name}
description: {Role/capability}. MUST BE USED for {specific scenarios}. Examples: "{trigger 1}", "{trigger 2}"
capabilities: [{portable capability names such as read_files, search_files, run_validation}]
---

# {Agent Role Title}

{One-sentence mission statement}

## Core Principles
- {Principle}: {Explanation}

## Process

### Step 1: {Name}
{Instructions}

## Output Schema

```json
{
  "field_1": "type and description",
  "field_2": "type and description"
}
```

## Constraints
- {Hard constraint}
- {Hard constraint}

## Handoff boundary

Your role as {agent-role} ends once {completed work}. At that point, write
your output and stop. Don't take the next action in the workflow — that belongs
to the orchestrator or the next agent. The reason: the orchestrator needs to
see your output before deciding whether to continue, retry, or escalate. An
agent that runs past its boundary makes that decision invisible.
```

**Capability Selection Patterns**:
- **Read-only**: `read_files`, `list_files`, `search_files` for analysis and review.
- **Research**: `retrieve_docs`, `search_web` when external facts are required.
- **Planning**: `write_files` for plans and docs.
- **Implementation**: `write_files`, `run_commands`, `run_validation` for scoped execution.
- **Orchestrator**: `delegate_tasks`, `track_state`, `run_validation` for coordination.

Map these capability names to runtime-specific tool names only inside the
target platform adapter.

## 5. hooks/

**Lifecycle automation.** Runtime-neutral rules and adapter notes for lifecycle
events. Platform adapters map these events into runtime-specific hook formats.

### lifecycle.json (manifest)

```json
{
  "version": "1.0",
  "skill": "{skill-name}",
  "events": [
    {
      "name": "before_tool",
      "rules": "hooks/rules.yaml",
      "on_block": "deny"
    },
    {
      "name": "after_tool",
      "rules": "hooks/rules.yaml",
      "on_block": "warn"
    },
    {
      "name": "before_response",
      "rules": "hooks/rules.yaml",
      "on_block": "block"
    }
  ]
}
```

### rules.yaml

```yaml
version: "1.0"
rules:
  - id: protect-generated-contracts
    match:
      paths:
        - "SKILL.md"
        - "skill-rules.json"
    action: warn
    message: "Review contract changes before publishing."
```

**Protocol**: generated hooks are portable rule manifests. Runtime-specific
adapters may translate them into local hook scripts, but generated plugin
scaffolds do not assume one vendor's hook event names.

## MCP Server (mcp/)

Optional MCP server scaffold for exposing tools, resources, or prompts to MCP
clients.

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("{service}_mcp")

@mcp.tool(
    name="{service}_health",
    annotations={
        "readOnlyHint": True,
        "destructiveHint": False,
        "idempotentHint": True,
        "openWorldHint": False,
    },
)
async def {service}_health(params: HealthInput) -> str:
    return "scaffold"

if __name__ == "__main__":
    mcp.run()
```

**Key rules:**
- Prefix tool names with the service name.
- Use schema-first inputs with Pydantic or Zod.
- Support JSON and Markdown response formats where useful.
- Include `--self-test` so generated MCP scaffolds can emit health JSON without optional runtime dependencies.
- Keep error messages actionable and avoid leaking internals.
- Ship MCP-specific evaluation questions beside the server scaffold.

## 6. scripts/

**Deterministic computation offloaded from LLM context.**

```python
#!/usr/bin/env python3
"""{Script purpose description}.

Usage: python -m scripts.{script_name} [options]
"""

import argparse
import json
import sys
from pathlib import Path


def process(input_data: dict) -> dict:
    """Main processing logic.

    Args:
        input_data: Parsed input from CLI args or stdin.

    Returns:
        Result dict to be output as JSON.
    """
    # Deterministic computation here
    return {"status": "success", "result": {}}


def main():
    parser = argparse.ArgumentParser(description="{Script purpose}")
    parser.add_argument("--input", type=Path, help="Input JSON file")
    parser.add_argument("--output", type=Path, help="Output JSON file (default: stdout)")
    parser.add_argument("--verbose", action="store_true", help="Print progress to stderr")
    args = parser.parse_args()

    # Read input
    if args.input:
        input_data = json.loads(args.input.read_text())
    elif not sys.stdin.isatty():
        input_data = json.load(sys.stdin)
    else:
        print("Error: Provide --input or pipe JSON to stdin", file=sys.stderr)
        sys.exit(1)

    # Process
    result = process(input_data)

    # Output
    output_json = json.dumps(result, indent=2)
    if args.output:
        args.output.write_text(output_json)
        if args.verbose:
            print(f"Written to {args.output}", file=sys.stderr)
    else:
        print(output_json)


if __name__ == "__main__":
    main()
```

**Key rules:**
- Always use `argparse` for CLI interface
- Support both `--input file.json` and stdin pipe
- Output JSON to stdout or `--output`
- Cross-platform: use `pathlib`, no shell assumptions
- Deterministic: same input = same output
- Importable: put logic in functions, gate main() behind `__name__`

## 9. data/

**CSV databases and lookup tables.** Stay queried via scripts; loading
wholesale into context defeats the point and will blow context windows
on tables of any real size.

```csv
id,name,category,value,description
1,item_a,cat_1,100,"Description for item A"
2,item_b,cat_2,200,"Description for item B"
```

**Always pair with a query script:**
```python
# scripts/query_data.py
import csv
import sys
from pathlib import Path

def query(data_file: Path, column: str, value: str) -> list[dict]:
    with open(data_file) as f:
        reader = csv.DictReader(f)
        return [row for row in reader if row.get(column) == value]
```

## 10. rules/

**Constraint definitions and validation rules.** Use explicit conditions,
operators, actions, and recovery messages.

```yaml
rules:
  - name: {rule-name}
    description: "{What this rule enforces}"
    conditions:
      - field: {field_name}
        operator: {regex_match|contains|equals|not_contains|starts_with|ends_with}
        pattern: "{pattern}"
    action: {warn|block|enforce}
    message: "{Message when rule triggers}"

  - name: {another-rule}
    description: "{Description}"
    conditions:
      - field: output_format
        operator: equals
        pattern: "json"
      - field: content_length
        operator: not_contains
        pattern: "TODO"
    action: warn
    message: "Output contains TODO placeholders"
```

**Operators**:
- `regex_match`: Python regex `re.search`
- `contains`: Substring check
- `equals`: Exact match
- `not_contains`: Inverse substring check
- `starts_with` / `ends_with`: Prefix/suffix check

## Matchers (matchers/)

Matcher docs explain what fields hook rules can inspect and which operators
are supported.

```markdown
| Event | Fields |
| --- | --- |
| bash | command |
| file | file_path, new_text, old_text, content |
| prompt | user_prompt |
| stop | reason, transcript |
```

Use matchers to keep hook behavior understandable before adding a full rule
engine.

## 11. evaluations/

**Eval cases, assertions, and quality measurement.**

Use the `expectations` field (plain strings) for grader-agent input — this is
the format `run_eval.py` and `agents/grader.md` consume. See
`references/schemas.md` `evals.json` for the canonical schema.

```json
{
  "skill_name": "{skill-name}",
  "evals": [
    {
      "id": 1,
      "prompt": "{Realistic user prompt}",
      "expected_output": "{Description of expected result}",
      "files": [],
      "expectations": [
        "The output includes {X}",
        "The skill produced {Y} file"
      ]
    }
  ],
  "trigger_evals": [
    {"query": "{should-trigger query}", "should_trigger": true},
    {"query": "{should-not-trigger query}", "should_trigger": false}
  ]
}
```

For machine-checkable structural assertions (file existence, regex match),
add them as an `assertions` array alongside `expectations` — the grader
reads `expectations`, automated validators read `assertions`. Keep both
when you have both; omit `assertions` when grader-readable strings are enough.

**Output templates consumed by scripts and generation modules.**

Shipped catalog:

|----------|-----------------|------|

| `templates/skill/technical-domain.md` | skill overlay generator | Technical workflow overlay |
| `templates/skill/creative-domain.md` | skill overlay generator | Creative output overlay |
| `templates/skill/current-events-trends.md` | skill overlay generator | Current-fact and recency overlay |
| `templates/skill/safety-sensitive.md` | skill overlay generator | Safety boundary overlay |
| `templates/skill/high-risk-professional.md` | skill overlay generator | Professional-risk overlay |
| `templates/skill/adversarial-edge-case.md` | skill overlay generator | Adversarial and edge-case overlay |
| `templates/skill/domain-injection.md` | skill overlay generator | Domain-injection guard overlay |
| `templates/skill/impossible-nonexistent.md` | skill overlay generator | Impossible-task boundary overlay |
| `templates/agent.md.j2` | `agents/` generator | Delegated-role prompt |
| `templates/command.md.j2` | `commands/` generator | Slash-command contract |
| `templates/hook.py.j2` | `hooks/` generator | Portable lifecycle hook adapter |
| `templates/mcp_tool.py.j2` | `mcp/` generator | MCP tool body embedded in server scaffold |
| `templates/plugin.json.j2` | `plugin/` catalog | Plugin metadata source template |
| `templates/surface_registry.json.j2` | `plugin/` catalog | Surface registry source template |
| `templates/schema.json.j2` | `schemas/` catalog | JSON schema source template |
| `templates/eval.json.j2` | `evaluations/` generator | Eval-set shell |
| `templates/rules.yaml.j2` | `rules/` catalog | Rule-set source template |
| `templates/matcher.md.j2` | `matchers/` catalog | Matcher/operator documentation shell |
| `templates/report.md.j2` | handoff docs | Verification or release report shell |

Template context contract:

- Root `templates/*.j2` files are source templates with a checked context
  contract. Agent, command, hook adapter, and MCP tool generation render from
  these templates.
- Required context fields are inferred from simple placeholders shaped like
  `{{ field_name }}`.
- Missing context fields are validation errors.
- Extra context fields are warnings so callers can prune unused data.
- Non-identifier template syntax is left for a future renderer; keep root
  catalog templates on simple placeholders until that renderer exists.
- Structured dict builders still own plugin manifests, surface registries,
  schemas, eval JSON, and hook rule YAML when preserving data types is safer
  than text substitution. Keep those builders explicit until a typed rendering
  layer exists.

Check the contract with:

```bash
python -m scripts.template_contract . --json
```

Current generator wiring:

- `templates/skill/base-universal.md` defines the generated SKILL.md section
  contract.
- `templates/skill/base-universal.md` is the base. The eight other
  `templates/skill/*.md` files are overlays selected from inferred category
  and risk tags, then inserted under `Applied Overlays`.
- `templates/agent.md.j2` renders generated `agents/*.md` files.
- `templates/command.md.j2` renders generated `commands/*.md` files,
  including plugin readiness commands.
- `templates/hook.py.j2` renders generated `hooks/hook.py`; `rules.yaml`
  keeps the generated destructive-command and sensitive-file guard rules.
- `templates/mcp_tool.py.j2` renders the Python MCP tool body embedded in
  `mcp/server.py`; the surrounding server keeps `--self-test` dependency-free.
- `templates/eval.json.j2` renders `evaluations/trigger_eval.json`.

Intentional structured builders:

- `plugin/plugin.json` and `plugin/surfaces.json` are assembled as Python
  dictionaries so paths can be derived from the actual generated file manifest.
- `schemas/*.json` are assembled as Python dictionaries so JSON types remain
  valid before any text rendering layer runs.
- `rules/*.yaml` uses the hook rule builder because it preserves default
  guardrail rules and recovery messages.
- `matchers/README.md`, `references/README.md`, `data/README.md`, and
  `examples/basic_usage.md` remain small deterministic docs until a user-facing
  preview command needs separate templates.

Example source template:

```markdown
# {{ report_title }}

**Status:** {{ status }}

## Summary

{{ summary }}
```

**Naming convention**: `{purpose}.{format}.j2` (for example,
`report.md.j2`, `schema.json.j2`, `rules.yaml.j2`).
