# Monitor SLO Parsing Rules

Monitor derives all observability config from declared SLOs. It never invents metrics or alert thresholds.

---

## Source of Truth

SLOs are declared in the Engineering gateway output: `modules/l4/engineering/` SLO declarations section and any project-level SLO document in `.wabblespec/state/plans/`.

Monitor reads declared SLOs only. It does not infer SLOs from code, logs, or past receipts.

---

## Parsing Rules

### DECLARED targets

For every SLO found in Engineering output:

| SLO field | Monitor derives |
|---|---|
| `metric_name` | Metric definition (type, unit, labels) |
| `threshold` | Alert rule threshold |
| `window` | Alert evaluation window |
| `severity` | Alert severity (critical / warning / info) |
| `description` | Runbook reference (required — see below) |

If any required field is absent from the SLO declaration, mark target as `UNDECLARED` rather than guessing defaults.

### UNDECLARED targets

When a metric or alert target cannot be derived from an Engineering SLO:

```
status: UNDECLARED
reason: "No SLO declared for <target>. Add SLO to Engineering gateway output before Monitor generates config."
```

Do NOT invent thresholds or default alert rules. Surface UNDECLARED targets in the Monitor receipt for human resolution.

---

## Runbook Required Per Alert

Every alert rule generated by Monitor must include a `runbook_url` or `runbook_path` field.

If Engineering SLO declaration does not include a runbook reference:
- Generate alert rule with `runbook_url: "REQUIRED — not yet declared"`
- Add to Monitor receipt: `alerts_missing_runbook: [list of alert names]`
- Do NOT block Monitor — surface as a warning, not a FAIL

Human must fill runbooks before Monitor output is deployed. This is enforced at Deploy gate, not Monitor gate.

---

## No PII in Log Schema

Monitor log schema output must not include fields that could contain PII.

**Prohibited log fields:**
- User identifiers (name, email, user_id, account_id, customer_id)
- IP addresses (unless declared in Engineering SLO as a required operational field)
- Request body content
- Authorization headers or tokens
- Free-text message fields without explicit sanitization declaration

**If Engineering SLO references a PII field for monitoring:**
- Replace with aggregate or hashed equivalent in Monitor output
- Note in Monitor receipt: `pii_fields_substituted: [list]`
- Do not include raw PII field in generated log schema

---

## Output Files

Monitor writes to `.wabblespec/observability/`:

```
.wabblespec/observability/
  metrics.yaml          — metric definitions derived from SLOs
  alerts.yaml           — alert rules with thresholds, windows, severities, runbook refs
  log-schema.json       — structured log field definitions (no PII)
  health-check.yaml     — health check endpoints and expected responses
  dashboard.json        — dashboard panel definitions (derived from metric definitions)
  monitor-receipt-<timestamp>.json
```

All files are overwritten on each Monitor run. Monitor output is always derived fresh from current SLO declarations.

---

## Regeneration Policy

Rerun Monitor whenever:
- Engineering SLO declarations change
- A new platform package is added
- Runbook references are updated

Monitor does not auto-run. Explicit trigger only.
